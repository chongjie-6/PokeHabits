# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Code style

Comments explain the non-obvious: an invariant, a workaround, a reason the straightforward version is wrong. Do not narrate what the code already says, restate the function name in prose, or leave section banners. If a comment would only paraphrase the line under it, delete it and let the naming carry the meaning.

## Architecture

`DESIGN.md` is the authoritative design document and is kept current; section numbers (§7.1, §13.2, …) are referenced from module headers throughout the source. Read the relevant section before changing anything in `lib/`.

**Local-first.** IndexedDB is the source of truth. Every route prerenders to static HTML; `POST /api/sync` is the only endpoint that touches replicated data, and the dynamic routes are it, `/api/auth/[...all]`, the two reminder routes (§8.5) and `/api/email` (§13.16). `proxy.ts` is the one piece of cross-cutting request code, matched on `/api` so the static shell keeps its CDN path (§13.17). Sync is replication between copies of the local store, not server-authoritative data — with `DATABASE_URL` unset the endpoint answers 503 and the app is fully functional. Setting nothing is a supported configuration (`.env.example`) — with none set the app runs exactly as it did before sync existed. `DATABASE_URL` turns accounts on, and in production drags two more with it: `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` are both fatal when missing (§13.12).

Data flow: React client components → `lib/store.ts` (in-memory cache + `useSyncExternalStore`) → `lib/db.ts` (IndexedDB, fire-and-forget writes) → `lib/sync/client.ts` merges server state in later. **The dependency runs one way**: sync imports the store; the store knows nothing about sync.

### Invariants that will bite

- **Mutations are synchronous and optimistic; the UI never awaits a write.** A habit tick that spins is a habit that dies (§7.2). Persist with the fire-and-forget `persist()` helper.
- **Two clocks (§13.2).** `updatedAt` (client epoch ms) decides merge conflicts; `seq` (one Postgres sequence) drives the pull cursor. Never compare or conflate them. `lib/db.ts:SyncMeta` keeps `cursor` (a `seq`) and `pushedThrough` (an `updatedAt` watermark) separate for this reason.
- **Last-write-wins ties break on content fingerprint**, not on "incoming wins" — otherwise two devices swap values forever instead of converging. The rule lives once, in `lib/sync/protocol.ts:wins`, and the server calls the same function the client does. Do not re-express it as SQL.
- **Deletes write tombstones**, never remove rows. Tombstones live in `state.tombstones`, out of `state.habits`, so no screen has to remember to filter them. Entries deliberately have no tombstone. Both halves collect a tombstone after `TOMBSTONE_TTL_MS` (six months, in `lib/sync/protocol.ts`, stated once like `wins`) — **the window bounds resurrection, not storage**: a device offline longer than that returns holding a live copy nothing contradicts any more.
- **The daily card has two corpora and one deck (§5.3).** `lib/deck.ts` holds the algorithm, generic over `{ id }`; `lib/quotes.ts` and `lib/facts.ts` each bind a corpus to it; `lib/daily.ts` is the only module that knows both, flattening either into a `DailyItem` so the card's three skins and the collection view stay single-variant. `Settings.dailyMode` picks between them and **syncs** — it decides what the app says to you, not how it looks. Favourites are one list across both corpora, so a count of "saved" has to be taken against the corpus on screen. A `Fact` requires its `source` where a `Quote`'s is optional: a fact has no author, so the source is the whole of its provenance.

- **`Settings.dailyTags` narrows the deck, and is checked for shape rather than membership (§5.4).** One flat list across both corpora, like `favourites`, which works only because the two tag unions are disjoint — `tests/daily.test.ts` pins that. `parseSettings` accepts a tag it has never heard of on purpose: the unions grow, and refusing the blob would stop a newer device syncing its habits over a tag name. Filtering to nothing a corpus has falls back to the **whole** corpus, so the card is never empty. Every function that answers a question about the _sequence_ — `dailyForDay`, `scheduleFor`, `deckCountFor`, `repeatGapFor` — takes the tags; `countFor` deliberately does not, because it is what there is to browse.

- **Undo is one slot with a TTL, and `lib/store.ts` does not import it (§7.4).** `deleteHabit` returns what it removed and the caller decides whether to offer an undo — the dependency runs one way, as it does with sync. `restore` re-stamps the habit **and every entry** with `Date.now()`: the delete wrote a tombstone stamped now, and anything restored under an older stamp loses that comparison and is quietly re-deleted by the next pull. The entries matter twice over, because `lib/server/sync-store.ts` deletes their rows outright when a tombstone lands — after a delete, the record `deleteHabit` handed back is the only copy anywhere. Do not add undo to "Delete all data" or a replacing import: both are confirmed twice under a danger heading, and the backup file is the answer there.

- **Creatures are derived, not collected (§5.5).** `lib/creatures.ts:discoveries` counts finished weeks at `QUALIFYING_RATE` from `buildHistory`, so deleting a habit can take a creature back. Every sprite in `data/creatures/` is original. Never add a character someone else owns.

- **`lib/insights.ts` and `lib/share-card.ts` are both derived and neither is persisted (§4.5, §4.6).** A null rate means "nothing was ever scheduled" and is drawn as an empty track — never a zero-width bar, which is the same mistake as making a rest cell look like a failed one. `weekdayExtremes` refuses to name a best and worst day below `MIN_SAMPLE`/`MIN_SPREAD`, and that reticence is the feature. The share card resolves its colours through `getComputedStyle` on a throwaway element, because `ctx.fillStyle` parses neither a custom property nor the `color-mix` the habit ramps are built from; its `geometry()` is exported so the one piece of arithmetic that can push a week off the edge of the image stays tested.

- **Dates are local civil `YYYY-MM-DD` strings (`DayKey`).** `lib/dates.ts` is the only module that should call `new Date()` to produce one; day maths is done in UTC-space to keep DST from shifting a boundary — `startOfMonth` lives there for that reason, and is what gives the trend whole calendar months rather than the grid's week-aligned window. It carries the largest share of the test suite.
- **Derived data is never persisted** — `lib/history.ts` and `lib/streaks.ts` rebuild a full year well inside the frame budget, pinned by `tests/history.bench.test.ts`.
- **Nothing user- or date-dependent may render on the server.** Routes are static, and the service worker caches that HTML — a server-computed date would pin every visitor to the build day's quote. Gate data-dependent subtrees on `store.hydrated`; read the clock through `useToday()`, not a `setState` in an effect. For state that lives in the browser rather than the store — `display-mode`, `beforeinstallprompt` — the `useSyncExternalStore` **server snapshot deliberately reports the hidden case**, so the UI only ever appears after hydration and never disappears. Writing it the honest way round makes the SW cache an install banner for someone who already installed.
- **Appearance never syncs, on any axis.** `theme` joined `skin` and `palette` as device-local (§13.8 #1) — `Settings` has no `theme` field, `lib/store.ts` does not import `applyTheme`, and `lib/use-theme.ts` is the React surface, shaped exactly like `lib/skin.ts` and `lib/use-palette.ts`. Two things keep the removal safe and both must stay: `lib/db.ts:readSettings` builds the blob field by field so a stale stored `theme` cannot ride a push, and `parseSettings` **accepts and drops** the field rather than rejecting it, because a device on an older build still sends it and refusing would stop it syncing habits too.
- **Signing in on a device that already holds habits stops for consent** (§13.8 #8). Nothing is uploaded while it waits: the session cookie exists, but `syncEnabled()` reads the local hint and withholding the hint is what holds the push. Both answers are non-destructive — "not mine" signs out rather than wiping the device, because on a borrowed phone those habits belong to whoever lent it.
- **`NEXT_PUBLIC_SYNC_ENABLED` is gone.** "Should this client sync" is now "is someone signed in", answered per device from a localStorage hint in `lib/session.ts`. The hint has **no authority** — it only buys permission to make a request the server may still 401, and the 401 path clears it. Never gate anything security-relevant on it.
- **`public/sw.js` must never cache `/api/`.** Its stale-while-revalidate rule covers every same-origin GET, and a cached session response tells a signed-out browser it is signed in — offline, where nothing corrects it. The early return for the API prefix is load-bearing.
- **Appearance is the one exception**: a blocking inline script in `<head>` (`lib/theme.ts:THEME_SCRIPT`) reads `localStorage` pre-paint, so theme is mirrored there as well as into IndexedDB. Any code path that changes theme must call `applyTheme`. The script now carries all three appearance axes — `theme` (synced), `skin` and `palette` (both device-local) — and its two palette regexes are load-bearing: stored values go straight into an inline style declaration, so it accepts a custom-property name and a six-digit hex and nothing else.
- **A custom palette wins by being inline, not by specificity** (§6.6). `lib/theme.ts:applyPaletteVars` writes the 20 colour tokens onto `document.documentElement.style`, which beats every `:root[data-skin=…]` block — so `app/globals.css` has no fourth skin and no skin knows palettes exist. It is also why nothing else may write inline styles to `<html>`. A palette is always complete for both modes; `normalisePalette` rejects a partial one rather than letting the rest fall through to the active skin. Habit colours, the `--habit-l-*` band, and every shape/type token are deliberately outside it.
- **The app was renamed from `hapi` to OpenHabits; four storage keys deliberately were not.** `lib/db.ts:DB_NAME`, `lib/theme.ts:THEME_KEY`, `lib/session.ts:HINT_KEY` and the `hapi_sync_seq` sequence still read `hapi`, because each names data that already exists on a device or in Postgres — renaming them orphans habits, flashes the wrong theme, or migrates a live counter. They are not leftovers to tidy up.
- **Reminders are a server feature and honest about it (§8.5).** The cron is **hourly**, not daily: "9am" is a wall clock and one daily run can only be nine o'clock in one timezone, so each subscription stores its browser's IANA zone and `lib/dates.ts:civilInZone` reads the clock there — the only function that reads a clock in a zone that is not this machine's. **Whether** a device is reminded lives in `push_subscriptions` (keyed on endpoint alone, the one table not keyed by `userId` — see its header); **when** lives in `Settings.reminderHour` and the optional `Settings.eveningReminderHour` (`null` is off), and syncs; each slot is claimed on its own `last_sent_*` column so one cannot silence the other. Delivery is claimed by the same `UPDATE … RETURNING` that selects it, so an at-least-once cron sends once. `/api/cron/reminders` fails closed with no `CRON_SECRET`. And §8.5's warning is load-bearing: `lib/reminders.ts` names every way a reminder cannot arrive as a distinct status and `ReminderCard` shows a switch in exactly one of them — do not collapse those branches into a boolean.

- **Outbound mail is handed off, not sent, when there is a queue (§13.16).** `better-auth.ts:deliver` awaits an _enqueue_, so §13.10's rule narrows rather than goes: a failed hand-off still throws, still rolls the sign-up back and still frees the address, but a send that fails after a successful hand-off is retried and then parked in the DLQ — an account can now exist while its verification mail is stuck somewhere nobody is watching. The link never enters a QStash message body, because a QStash body is retained and a verification URL is a session (§13.12): the envelope goes to Redis under a random id with an hour's TTL and the message carries the id. `dequeueEmail` reads rather than claims, which is the **opposite** of `lib/server/reminders.ts` — there a retry is the thing to prevent, here it is the whole point — so a missing envelope is answered 200, never an error. With no `QSTASH_TOKEN`, and on localhost whatever the token says, mail is sent inline exactly as before.

- **`lib/server/ratelimit.ts` fails open, and it is the only gate here that does (§13.17).** An unreachable store is not evidence of abuse, and a Redis outage that 429s the site hands an attacker the outage as a denial of service — so a timeout, an error or an unattributable IP is a request _allowed_. Two things must not drift: `metered()` is the single statement of which endpoints are excluded (`/api/email` and `/api/cron/…`, both machine-authenticated) and `proxy.ts`'s matcher is deliberately broad rather than repeating it; and a 429 in `lib/sync/client.ts` must never take the 401 path, which clears the signed-in hint — that would sign a device out for being busy — nor the `retry` path, which loops immediately.

- **`--muted` passes WCAG AA with no headroom.** Never apply an opacity modifier to it (`text-muted/80` and friends were all removed in an audit). If something needs to recede further, give it a smaller role, not a thinner colour.

### Server side

**Every table is under row-level security, and `lib/server/scope.ts` is the only way in** (§13.15). `asUser` opens a transaction-local `openhabits.user_id`; the policies compare rows to it, an unset setting is NULL, and a policy that is not true denies the row — so a query outside a scope reads nothing rather than everything. Transaction-local matters: `db.ts` pools connections across an instance's concurrent requests, and a session-scoped setting becomes the identity of whichever request checks that connection out next. Two statements in `0006` are hand-written and load-bearing — `FORCE ROW LEVEL SECURITY`, which drizzle-kit cannot generate and without which the policies never fire for the table owner, and a superuser warning, because a `BYPASSRLS` role ignores everything silently. `asServer` is the one scope that is not an account: granted only on `push_subscriptions` and `select` on `settings`, for the sweep's cross-account scan and the endpoint handover the subscribe upsert performs. **`habits`, `entries` and `users` have no bypass anywhere.** The `where user_id = …` clauses stay — both halves are load-bearing, and the redundancy is the design. `tests/server/rls.test.ts` is the only test that runs as a non-superuser role, because a superuser passes every RLS test ever written.

`lib/server/` is the only server code apart from `workers/`, which holds what a machine calls: `workers/email.ts` is the QStash worker behind `/api/email` (the route keeps only segment config), and `workers/reminders.ts` is the Cloudflare cron that calls `/api/cron/reminders` — deployed by wrangler, which bundles it alone, so nothing else in that directory may be imported from it. `auth.ts` is the identity seam and **Better Auth fills it** (`better-auth.ts`, email + password, same Postgres); `resolveUser` is the only way in, so swapping providers rewrites one function. It fails closed — anything but a valid session is 401, with no bypass. **The auth origin is configured, never inferred** (`base-url.ts`, §13.12): the origin Better Auth resolves is the one it mails verification links into, inference takes it from the `Host` header, and `send-verification-email` accepts any address with no session — so production throws rather than guess. Every table is keyed by `(userId, …)`; `runSync` takes `pg_advisory_xact_lock` on the account so commit order matches `seq` assignment order.

**`auth-schema.ts` tables are separate from `schema.ts:users` on purpose.** `user` is the identity Better Auth owns; `users` is the account sync rows cascade from. Same id, no foreign key, linked by the upsert in `sync-store.ts`. Do not merge them — a dependency's migrations would gain authority over the table holding every habit. `SyncUser` lives alone in `auth-types.ts` so `sync-store.ts` can name its argument without importing an auth stack (this is what keeps the PGlite test runnable).

Better Auth's four tables live in a `pgSchema("auth")`, so `auth.user` and `public.users` are told apart by name rather than by one letter (§13.8 #9).

Migrations are generated, reviewed and committed — never `drizzle-kit push`, which can resolve a rename by dropping the column, and these tables hold history that exists nowhere else. **`0005` is hand-written** for the same reason: drizzle-kit cannot tell a table that changed schema from one dropped and recreated, and it takes the destructive reading without asking. Its snapshot in `drizzle/meta/` was hand-edited to match — the check that they agree is `npm run db:generate` reporting no changes, so run it after any schema edit and treat unexpected output as a real finding.

### Known gaps

A dormant push subscription is now aged out after `SUBSCRIPTION_TTL_MS` against a `last_seen_at` that `touchReminders()` refreshes on app start — so the column only means what it says as long as that call stays on the app-start path. Password reset exists (§13.13): a one-hour single-use link, all sessions revoked on use, and **the same answer whether or not the address has an account** — do not add a branch that reports whether the send found one. Verification **is** required to sign in (§13.10, reversing §13.9): sign-up returns no session, the link in the mail creates one (`autoSignInAfterVerification`), and an unverified sign-in attempt 403s and resends. The Gmail SMTP credentials (`SMTP_USER` / `SMTP_PASSWORD`, via nodemailer) are still optional like everything else — and `requireEmailVerification` follows them, because requiring a click no mail can deliver would break sign-up entirely on a deployment with no mailer. With a mailer configured a failed send now **fails the sign-up** (Better Auth rolls the transaction back, freeing the address); with none it logs and keeps the account, as before. The client must not set the signed-in hint on a sign-up — `token` is null — or sync collects 401s for as long as the mail goes unread. Signing in merges whatever is on the device into the account (§13.8 #8). Open questions are listed in DESIGN.md §12 and §13.8 — check them before "fixing" something that was decided deliberately. `ROADMAP.md` puts those questions in order and marks which ones are settled decisions rather than pending work.

DESIGN.md records reversals rather than overwriting them: §8.4 now intercepts `beforeinstallprompt` after originally refusing to. When a section reads as a reversal, the current behaviour is the one described second.
